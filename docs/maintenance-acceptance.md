# 新业务仓库的两类测试

本清单用于测试环境验收。代码、本地模拟和单元测试通过，不等于这两类真实测试已执行；新仓库由维护人员创建后再填写实际链接和结果。

## 准备测试仓库

将 [测试文档样例](../examples/business-repository) 中的 `zh` 目录复制到新业务仓库根目录，提交到默认分支。样例包含目录介绍、排序、正文、页内锚点和本地图片，内容明确标记为维护流程测试。

首次接入申请可填写：

| 字段 | 测试值 |
| --- | --- |
| 登记 ID | 新的稳定 ID，例如 `maintenance-test` |
| 来源仓库 | 实际的 `owner/repository` |
| 分支 | 实际默认分支，通常为 `main` |
| 语言 | `zh` |
| 目标栏目 | `cases` |
| 分类路径 | `应用案例 / 教学与实践` |
| 子类节点 ID | 已知时填写；只填写分类路径也可以选择已有子类 |
| 目标路径前缀 | 独立测试前缀，例如 `maintenance-test` |
| 目录层级 rootDep | `1` |

开始前确认：测试仓库可被流水线读取；测试环境中已有目标分类；维护人员权限、检查、预览和结果回报已接通。私有来源应先具备所需的只读访问。测试来源的所属账户/组织需与测试执行环境的来源设置一致。登记和发布都以具体 PR 为准，不用直接编辑配置文件。

## A. 新仓库注册

1. 提交“文档仓库接入或调整”Issue，得到登记 PR。
2. 核对仓库地址、语言、分类路径及 ID。登记检查应验证所选仓库和分支可读、对应语言有 Markdown；不因本次接入去检查或发布其他不相关来源。
3. 文档团队手动合并登记 PR，原 PR 回报“接入登记完成”，并生成首个候选发布 PR。
4. 候选清单应包含新仓库的固定提交和目录子类。首个独立仓库使用独立关联组，不应把现有全部仓库塞进同一个 PR。
5. 检查正文、图片、锚点、目录和排序，打开预览。候选 PR 未合并前，正式可见内容保持原状态。
6. 文档团队合并候选 PR，查看同一 PR 的发布结果回报；“任务已受理”与“发布成功”分开，相关同步未完成时保持“发布中”。未启用外部同步的本地模式明确显示“本地发布完成”。
7. 在测试站确认路径为“应用案例 → 教学与实践 → 测试文档”，打开测试步骤页，确认 `REGISTER-V1`、图片与锚点可用，来源原地址保持不变。

记录：接入 Issue、登记 PR、首个候选 PR、来源 SHA、最终回报、测试站地址和实际结果。

## B. 业务 PR 合并触发更新

1. 在业务仓库新建分支，将 `zh/guide/steps.md` 的 `REGISTER-V1` 改为 `MERGE-V2`，提交业务 PR。
2. 业务 PR 未合并时，测试站保持 `REGISTER-V1`。
3. 合并业务 PR，确认生成或更新对应引用关联组的候选发布 PR，清单锁定具体 SHA。候选尚未合并时，测试站仍保持上一版。
4. 在同组候选 PR 未合并时，再合并一次业务修订；应更新同一个发布 PR，并对新修订重新检查，旧修订的检查不得放行新内容。
5. 加入一个不存在的 Markdown 链接并合并业务修订：候选应检查失败，PR 回报失败位置与检查入口，不能正式发布。修复链接再合并，应继续更新该候选 PR 并重新检查。
6. 文档团队检查预览后手动合并候选，等待最终结果。测试站应显示最新已确认标记，仍位于原子类，且没有重复目录。
7. 重复投递同一合并事件或重试执行，不应重复建发布 PR、重复目录或重复结果评论。旧任务不得覆盖新修订的状态。

若需要验证真实跨仓库关联，再加入一个可读、已登记的测试来源：A 引用 B，B 引用 C 时应同组；未关联 D 保持独立。关联组扩大时替换旧候选，保留关闭说明，不能继续合并过期候选。

## 结果判断

| 观察结果 | 判断 |
| --- | --- |
| 只增加了登记文件 | 仅登记完成，不算发布通过 |
| 只生成了候选 PR 或预览包 | 尚待人工确认 |
| 执行请求已受理 | 还需查看最终回报 |
| 工作流超时或中断 | 状态待核对，不能推断已回滚 |
| 同步失败 | 保留失败结果，修复后重试并更新同一结果评论 |
| 回报发送失败 | 发布结果保留并重试回报，不重复执行发布 |
| 最终回报通过且测试站内容、目录、资源一致 | 对应测试用例通过 |

本轮测试不把数据库事务回滚等同于完整部署回滚；整站探测及恢复上一完整版本的验收另行进行。
